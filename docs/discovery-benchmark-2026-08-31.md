# 订阅商店与内容发现：全面对标与「AI 探索」功能设计报告

> 生成日期：2026-08-31 ｜ 方式：3 个并行子代理（发现机制对标 30+ 产品 / 商店现状审计含实测普查 / 供给源与可行性调研含真实管线验证）
> 性质：研究与设计，未做任何功能实现。配套实测脚本：`scripts/diag-store-census.js`（目录普查）、`scripts/diag-discovery-feasibility.js`（发现管线验证，6/6 站点跑通）
> 前置阅读：`docs/audit-benchmark-2026-08-30.md`

## 0. 结论速览

1. **你的直觉被数据完全证实，且实际情况更严重**。商店目录实测 190 条（去重 183），**中文源仅 21%**（与大陆目标用户严重错配）；抽样 20 源 4 个不可达，外推 **约 1/4 源在大陆直连环境不可用**；375 个公众号押注的第三方桥**实测已被封禁（ECONNRESET 全灭）**；卡片上的评分/订阅数是哈希生成的假数据；5 个专题包里 3 个存在 URL 漂移（整包订阅会静默丢源）。
2. **发现机制行业分五类**（编辑目录/算法推荐/AI 探索/社区传播/导入迁移），成熟产品全部是混合结构；纯静态目录（我们的现状）是唯一没有自我更新能力的模式——Inoreader Bundle 目录的式微就是前车之鉴。
3. **「AI 探索」功能可行且性价比极高**：最难一环「站点→可用 feed→元数据」已用产品现有解析器实测跑通（6/6）；候选池有 4000+ 条免费合规现成数据（GitHub awesome-lists + ooh.directory）；单次探索 LLM 成本约 **¥0.10**（验证抓取零 token）。
4. **三条必须守住的红线**：手动触发（RSS 品类反算法，NetNewsWire 立场即品类立场）；只展示经过本地验证的源（LLM 引用幻觉率实测研究 28-47%，AI 只能出候选不能出结论）；探索结果绝不混入订阅时间线。
5. **差异化王牌**：本地兴趣画像驱动的归因解释（"因为你常读 X、保存过 Y"）——云端竞品（Folo/Feedly）受隐私架构限制做不到，这是我们该占的位置。

## 1. 现状诊断：订阅商店的六个病灶（全部有实测证据）

### 病灶一：假——质量数据是装饰品
- 评分 `4.3 + sin哈希(rank)×0.6` 恒在 4.3~4.9；订阅数按 rank 指数衰减（`feed-store.js:159-165`）。每张卡片的 ★ 评分和「xx 万订阅」全是哈希假数据。
- 头部文案「每一源都由编辑人工核验」（`feed-store.js:284`）无任何核验记录支撑；公众号搜索卡「375」是硬编码计数。
- 用户据假数据做的每个订阅决策都是错误决策。

### 病灶二：死——约 1/4 源直连不可用，且无巡检机制
- 确定性抽样 20 源：16 存活、4 失败（Discord/Google Research 超时=被墙、公众号主桥 ECONNRESET）；外推 **35±10 源不可达**，叠加未标注境外源后风险面约 40-50 个。
- **公众号单点故障已爆发**：375 个号全部指向 `wechat2rss.bestblogs.dev` 单一第三方桥，实测连续 ECONNRESET；备用 `hub.slarker.me` 也超时；URL 是内容哈希无法自建。整个公众号体系当前在目标网络环境下归零。
- 仓库里上一轮实测 `audit-store-result.json` 显示 47 个失败源中**约 25 个至今仍在目录里**；目录无自动巡检，死源清理纯靠人工记得跑脚本。
- 境外高危源 10 条中 5 条未标「需代理」；1 条 http 明文（arxiv）无任何提示。

### 病灶三：少且错配——总量 190、中文仅 21%、无长尾
- 190 条 vs Feedly「数百万」、Folo「1.3M feeds」：量级差 4 个数量级。分类失衡（ai 42、eng 34、matlab 4）。
- **语言错配是最刺眼的问题**：EN 源 150 条（78.9%）、中文 40 条（21.1%），而我们目标用户的主要阅读语言是中文。
- 描述平均只有 25 字，用户无法据此判断「这个源里到底是啥」。

### 病灶四：目录内部数据卫生欠账
- 7 条重复 URL（extra2 补充批次与主目录未去重）；目录自述与实际漂移（自称「TOP 100」实际 rank 到 318、1-100 缺 24 个 rank——删源留下的疤痕）；专题包 3 处 URL 漂移导致整包订阅静默丢源；无 siteURL 字段（订阅时才推导）。

### 病灶五：断——发现、订阅、管理三处割裂
- 搜索只在 190 条目录内过滤，**搜不到就是死路**，没有任何外部发现路径。
- 订阅成功只有一行小字：不预取、不展示该源最新文章、不跳转、没有「去读第一篇」——addFeed 其实已把首批文章入库了，UI 没用上。
- 商店与已订阅完全隔离：已订阅卡片只是禁用态，不能反向跳转到该源列表；订阅管理在侧栏，两套世界。
- 批量订阅失败静默跳过；免费 30 源门控在批量订阅第 31 个源时只把升级提示塞进小字。

### 病灶六：个性化资产齐备但与商店零交互
- EvolutionEngine 兴趣画像（29 个技术词标签、源偏好、30 天半衰期、skip 负样本）、reading_behavior 行为流（7 种动作带权重）、feed_health 健康监测（成功率/连续失败/is_dead）——**「用户喜欢什么」「源活得好不好」的原始数据全都有**，但商店按录入顺序 rank 排序，与这些数据零交互；「你可能喜欢」只作用于已订阅内容池。

## 2. 对标：发现机制的五种模式与行业经验

### 2.1 模式分类学

| 模式 | 机制 | 成功案例 | 失败/失效案例 |
|---|---|---|---|
| 编辑目录（人工策展） | 人工收录/分类/精选 | Apple Podcasts 编辑位、App Store Today、ooh.directory、阮一峰周刊、awesome-lists | 静态不更新则腐烂（Inoreader Bundle 式微=我们现状）；FeedSpot 引入付费排名后信号全毁 |
| 算法推荐 | 全站行为排序 + 画像个性化 | Folo 热门榜（订阅数排序）、Pocket Casts Trending、Apple Listen Now | Artifact 死于互动不足却硬做全量推荐；YouTube 反馈按钮仅约 11% 有效；微信折叠订阅流持续反弹 |
| AI 探索（生成式发现） | AI 按兴趣在候选池/开放网络找源，配解释与引用 | **Folo Discover（"AI finds the best sources across the open web"，直接先例）**、Perplexity Discover（引用+追问）、Kagi News（社区源+AI 解读分层）、Particle Radar | 「AI 替你决定看什么」的全量推送形态（Artifact）；Kagi 摘要失真争议说明解读层需克制 |
| 社区传播 | 好友订阅/作者互推/分享流 | Substack Recommendations（订阅成功瞬间弹推荐）、NewsBlur blurblog | Matter 砍掉 Network、Omnivore 无社交——小工具用户密度不够，两度失败 |
| 导入迁移 | OPML 导入、关停产品迁移页 | Pocket 关停→各家迁移页收割 | 零和游戏，不创造新需求 |

**核心规律：成熟产品都是「编辑位 + 榜单/算法 + 个性化」的混合**（Apple Podcasts、Pocket Casts），纯静态目录必然腐烂。

### 2.2 RSS 品类的四条特殊规律（为什么商店普遍做不好）

1. **供给侧结构性萎缩**：独立博客关站、封闭生态（公众号）不给 RSS——目录只会越放越旧。
2. **需求低频且排他**：订阅是「一次决定、长期沉默」，用户逛商店动机天然弱；而 RSS 用户恰是反算法人群，硬塞推荐流会引发反感。
3. **质量信号稀薄**：没有点赞/转发/完读，唯一诚实的信号是**订阅数**（Feedly/Folo 用它做第一排序）和**存活状态**（更新频率、死链检测）——静态目录连这个都拿不到。
4. **质量判定成本高**：判断一个源值不值得订需要读几周——只有「内容预览 + AI 解释」能把这个成本压缩到 30 秒，这正是 AI 探索的价值原点。

### 2.3 八条可直接借鉴的机制

1. **探索 = 一期「为你定制的周刊」**（阮一峰式单人策展的自动化）：包装成策展人而非推荐引擎，契合品类心理。
2. **候选池建在社区策展之上，不自建**（RSSHub 路由生态、ooh.directory、Kagi News「AI 不选源只解读」的分层）。
3. **源卡片 = 客观指标 + 本地归因解释**（Folo 卡片字段 + 可解释推荐研究）。
4. **探索前 30 秒兴趣声明**：「基于我的订阅」或「输入想深入的领域」（Feedly 官方工作流、Perplexity 个性化演进）。
5. **结果带真实样章预览，绝不混入时间线**（微信折叠订阅流的反弹 + Artifact 之死 + Kagi/Perplexity 引用规范）。
6. **订阅成功的瞬间是第二探索入口**（Substack 机制）：「已订阅，要看 3 个类似源吗？」
7. **反馈闭环要可见**：不感兴趣三键 + 探索风格三档（保守/平衡/大胆），把 exploration 做成用户可见的滑杆（AWS Personalize 参数化思路 + YouTube 反面教材）。
8. **商店改版为「日历化策展 + 榜单」双层**，静态目录降级为底座（App Store 选题日历 + awesome-lists 除名规则）；**付费与排序严格隔离**（FeedSpot 教训）。

## 3. 「AI 探索」功能设计

### 3.1 产品定义

- **入口**：订阅商店顶部「AI 探索」按钮 + 订阅成功页「发现类似源」副入口。**仅手动触发**。
- **前置**：可选兴趣声明（默认「基于我的订阅画像」，可切换「手动输入一个领域」，如「想深入了解编译器」）。
- **输出**：每次 10 张源卡片。每张含——
  - 客观层（本地验证产物）：最新更新时间、更新频率、单篇平均深度（全文/摘要）、语言、条目规模；
  - 内容预览：最近 3 篇真实文章的标题 + 开头摘要（不是 AI 编的）；
  - AI 解释：定位 / 风格 / 适合谁 / 更新规律 / **为什么推荐给你**（引用本地画像：「你常读 X、保存过 Y」）；
  - 动作：一键订阅 / 不感兴趣（太泛 / 已有类似 / 领域不符）/ 稍后再看。
- **硬约束**：不与商店目录、已订阅、历史探索结果重复（URL 归一化 + 域名级去重）；**未通过本地验证的候选永不展示**；不进入订阅时间线；会员与免费的区别只在探索次数与解释深度，排序永不收费。

### 3.2 管线设计（六步，含现有代码复用映射）

```
兴趣画像/领域 → 候选生成 → ①发现 → ②验证 → ③评分 → Top10 → ④解释 → ⑤去重 → 卡片流 → ⑥反馈
```

| 步骤 | 设计 | 复用 |
|---|---|---|
| 候选生成 | LLM 规划调用：画像 top 标签 + 内置候选池摘要 → 挑 15 个域名级候选（可少量外扩新域名）。**LLM 幻觉率 28-47%（实测研究），所以 AI 只出候选、本地验证说了算** | LLMService.complete（:42-60） |
| ①发现 | 站点首页 `<link rel="alternate">` 解析 + 常见路径猜测（/feed /rss /atom.xml /feed.xml /index.xml /rss.xml，base 与 host 根两轮）→ 并发验证。**新增 FeedDiscovery 模块约 80 行**（最难一环已实测跑通 6/6） | FeedService.fetchFeed（:20-58）+ FeedParser.parse（:53-60） |
| ②验证 | 条数、最新发布时间、中位更新间隔、平均正文字符、全文/摘要判定（≥800 字）、语言（CJK 占比）；GBK 等编码复用现有探测 | FeedParser.decodeBuffer（:29-51）、Models.plainText |
| ③评分 | S = 25·freshness + 15·regularity + 20·depth + 15·hitRate + 10·language + 10·fullText + 5·size（参数已用真实站点标定：阮一峰 5460 字=全文 1.0、sspai 89 字=摘要 0.03、云风 14 天周更长文型、爱范儿日更高频型） | KnowledgeEngine.autoTagEntry（29 词正则，零 LLM）+ EvolutionEngine.interestProfile |
| ④解释 | 最近 3-5 篇标题+开头段 → 结构化中文解释（JSON 输出），仿 richSummary 加一个 explainFeed 方法 | LLMService + ArticleChunker.truncate + sanitizeLLMText（:317-339） |
| ⑤去重 | URL 归一化（协议/utm_*/&amp;/feedburner 解包）+ **注册域级去重**（对商店 190 + 已订阅 + 公众号表 + 历史探索） | AppStore._entryExistsByURL 同款归一化（:747-756）+ 新表 explored_feeds |
| ⑥反馈 | 订阅 → review 行为加分；「不感兴趣」→ 域名负向 -2 + 永久拉黑；忽略 → 只记不发信号 | EvolutionEngine.recordBehavior/_bumpInterest（:135-167）全部现成 |

### 3.3 候选池供给（构建期快照，运行期零依赖）

| 渠道 | 实测规模 | 协议 | 结论 |
|---|---|---|---|
| chinese-independent-blogs（GitHub） | **1340 个中文博客 feed**（表格含 Feed 列） | MIT | **主力**，直接补中文短板 |
| plenaryapp/awesome-rss-feeds | 40 个分类 OPML | CC0 | 主力（OPML 解析器已有） |
| ooh.directory | 2433 个英文博客 + 140 分类，robots 全开 | 无风险 | 英文补充 |
| 纯 LLM 外扩 | 无上限 | 幻觉率 28-47% | 只出域名候选，必须过验证 |
| RSSHub 公共实例 | 3000+ 路由 | 公共实例实测 403/503 | 降为扩展：只支持用户自建实例 |
| 公众号 | 375 内置表 | 桥靠人工维护 | **不进探索范围**，继续走商店内置 |

构建期脚本生成内置快照 JSON（约 4000 条，几百 KB），运行期不依赖 GitHub 可达性。

### 3.4 成本、隐私与降级

- **成本**：一次探索 = 1 次规划调用 + 10 次解释 ≈ **¥0.10**（DeepSeek 牌价；验证抓取是本地行为零 token）。1 次探索 = 1 次 AI 额度（对用户有利：低于一篇长文摘要的成本）。
- **隐私**：进 prompt 的只有兴趣标签 top-5 + 候选源内容片段，**已订阅列表不进 prompt**；入口放一句静态披露。本来就是用户自己的 key 自己的请求，无需新机制。
- **降级**：无 key → 「非 AI 版探索」（内置池按分类出 10 个 + 本地验证，只有元数据无解释）；全部候选验证失败 → 空态 + 重试（分层：LLM 外扩 → 快照兜底）；LLM 失败 → 元数据卡片照出 + 单卡重试解释。**永不展示未验证源**。

### 3.5 MVP 切分

**做**：FeedDiscovery 模块（diag 脚本代码直接转化）→ 候选快照构建脚本 → `exploreFeed` IPC → 商店「AI 探索」标签页卡片流（复用现有卡片样式）→ explored_feeds 去重表 + 反馈写回 → 一句隐私提示 + 非 AI 降级。
**后置**：RSSHub 自建实例对接、已订阅正文抽友链自举、公众号探索、OPML 分享社区。
**顺带修复的存量痛点**：FeedDiscovery 挂入 addFeed 前置——用户粘贴博客首页就能订阅（现状直接报错），这是探索管线免费的副产品。

## 4. 超越 AI 探索：发现体系的整体加强（八个维度）

| 维度 | 现状 | 建议动作 | 优先级 |
|---|---|---|---|
| **供给** | 190 源、中文 21%、写死在 4 个 js | 从 1340 中文博客快照精选 100-200 条入目录（一次把中文占比拉到 ~50%）；候选池快照作为目录的「可扩展底层」 | 高 |
| **质量信号** | 假评分/假订阅数 | **换成真实可验证指标**：更新频率、最近更新时间、单篇深度、存活状态（feed_health 已有数据底座）；订阅数在没有服务端前不展示——宁可空缺不放假数据 | 高 |
| **治理** | 无巡检、死源留存 25+、专题漂移 3 处、7 条重复 | 把 diag-store-census 纳入发版前例行检查；feed_health.is_dead 回馈商店（降权/标灰/「最近失效」提示）；修专题 URL 与重复条目 | 高 |
| **呈现/决策支持** | 25 字描述、无预览 | 源卡片加「最近 3 篇标题」预览（addFeed 已入库首批文章，UI 直接用）；搜索不到时给「AI 帮你找」出路 | 中 |
| **场景嵌入** | 订阅成功即终点 | 订阅成功页「去读第一篇」+「发现类似源」副入口（Substack/NewsBlur 模式） | 中 |
| **反馈闭环** | 无 | 探索结果三键反馈 + 写回画像；让用户看见效果（「下次将排除此类」） | 中（随 MVP） |
| **信任红线** | 「人工核验」文案无据 | 删除无据文案；探索永远手动触发、不进时间线、不暗改订阅列表 | 高（红线） |
| **商业化边界** | 免费 30 源门控已与批量订阅冲突 | 探索次数会员分层（免费 1 次/周、会员不限）可做；**探索结果排序与展示永不收费**（FeedSpot 教训）；批量订阅的门控提示改对话框引导 | 中 |

## 5. 风险与红线汇总

1. **LLM 幻觉**：只出候选；未验证不展示；解释基于真实抓取的样章而非模型记忆。
2. **反算法红线**：手动触发、独立板块、不折叠不插入订阅时间线（微信 2018 改版的用户反弹 + NetNewsWire 品类立场）。
3. **公众号单点故障**：眼下就该做的事——公众号卡片在主桥不可达时给出明确降级提示（当前是静默失败）；中期评估 wewe-rss 自建引导与多桥备份。
4. **冷启动**：无画像用户（新装）探索退化为「按领域+分类热门」，用兴趣声明补；新源冷启动天然靠 feed 内容特征（比电商容易）。
5. **付费隔离**：任何排序/展示位置不与会员挂钩。

## 6. 建议实施顺序

- **第 0 步（独立小修，不依赖 AI）**：商店治理——去重 7 条、修 3 处专题漂移、feed_health 回馈商店（死源降权/标注）、伪数据替换为真实指标、补 100-200 条中文源、批量订阅门控对话框化、公众号桥降级提示。
